# e-store-backend

An e-commerce application written in Go

## Supply chain security

Every image published to GHCR from `main` carries two signed [GitHub Artifact
Attestations](https://docs.github.com/actions/security-guides/using-artifact-attestations-to-establish-provenance-for-builds),
produced by the CI pipeline and bound to the image digest:

- **SLSA build provenance** — proves *how and where* the image was built (this
  repo, commit, workflow and runner).
- **SBOM** (SPDX, generated by [Syft](https://github.com/anchore/syft)) — a full
  inventory of *what is inside* the image (Go modules and OS packages).

Both are signed keylessly via [Sigstore](https://www.sigstore.dev/) (no
long-lived keys), recorded in the public Rekor transparency log, and pushed to
the registry as OCI referrers alongside the image.

### Verify a published image

The [`justfile`](justfile) wraps both attestation checks and the registry
referrer tree in one recipe:

```sh
just verify-image          # verifies :latest
just verify-image v1.2.3   # …or a specific tag
```

Or you can also copy the commands from the recipe and run the checks directly.

> For stronger guarantees, verify against an immutable `@sha256:…` digest
> rather than a mutable tag, and pin the producing workflow with
> `--signer-workflow MurtadhaInit/e-store-backend/.github/workflows/ci-publish.yml`.

### Vulnerability & misconfiguration scanning

[Trivy](https://trivy.dev/) runs at two stages of the pipeline, with findings
surfaced in the repository's **Security → Code scanning** tab:

- **Filesystem scan** (every push and PR) — known CVEs in Go modules, Dockerfile
  and IaC misconfigurations, and hardcoded secrets. Scanner selection and
  severity policy live in [`trivy.yaml`](trivy.yaml).
- **Image scan** (published images only) — re-scans the pushed image by digest
  for OS- and library-level CVEs.

Both report at `CRITICAL`/`HIGH` severity and skip unfixed vulnerabilities; they
surface issues rather than fail the build.
